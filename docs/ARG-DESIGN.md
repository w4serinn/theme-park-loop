# ARG設計ドキュメント(隠しページ群の全体設計)

このファイルは `docs/ROADMAP.md` の「### 13. 隠し用語集ページ群」を、
ARG(代替現実ゲーム)的な「発見の連鎖+謎解き」に拡張するための設計図。
evolveループはこのファイルを見ながら`### 13`のサブタスクを進め、
ページを1つ実装するたびに該当行のstatusを更新する。

**現時点ではページ番号(P1, P2…)による骨組みのみを定義している。
実際のページタイトル・本文・具体的な暗号内容はまだ決まっていない。**
各ページを実装する段になったら、このファイルの当該行にタイトル・実ファイルパスを
追記していく(一方向の充実。既存の`roadmap-done.md`と同じ運用)。

---

## 1. 基本コンセプト

- サイト内の「気になる単語」を検索すると、どこからもリンクされていない隠しページに
  たどり着く、という発見型の遊び(既存の仕組みをそのまま踏襲)。
- 隠しページは全て「フレーバー」という1種類の存在として扱う。「本筋の特別なページ」
  という別カテゴリは作らない。
- フレーバーページの一部は「断片」を産出する。断片の使い道は2種類:
  1. 別のフレーバーページの謎(暗号など)を解くために必要(**中間断片**)
  2. 最終的な「扉ページ」を開くために必要(**扉用の断片**)
  中間断片は扉ページには直接使われない。扉ページが要求するのは扉用の断片のみ。
- フレーバーページの多くは断片を産出しない、ただの読み物(発見自体が報酬)。
- 全体は「木」ではなく「網」の構造。あるページが1つの親ページからしか
  たどり着けない、とは限らない。複数の異なるページの本文にたまたま同じ単語が
  出てくれば、どちらから見つけてもよい(4節の表で親IDが複数書かれている行を参照)。
  「たどり着き方」(発見経路)と「必要な断片」(その場で解くために必要な材料)は
  別軸であり、複数経路で来れるページでも、必要な断片はどの経路でも変わらない。
- 一部のフレーバーは新規ページではなく、**既に実装済みのページの中の
  インタラクション**(例: 学院案内のマスコットをクリックして出るセリフ、
  料金シミュレーターで特定の金額にすると現れるテキスト)として実装される。
  この場合、新規HTMLファイルを作らず、既存ページのJS/HTMLに追記する形になる。
- 扉ページを開くと、校長からの手紙+本当の入学案内ページ(ゴール)が現れる。
  既存の`pages/tickets/index.html`(来園者向けチケット案内)とは別物として新設する。

## 2. 検索の仕組み

### 2-1. 複数の言い回しでヒットさせる(`keywords`)

現状の検索(`src/search.js`)は`title`+`category`の部分一致でヒットを判定している。
これだと実質「そのページの正式名称に含まれる文字列」でしか見つからない。
しかし網状構造では、同じページに複数の親ページから辿り着けるが、各親ページの
本文では別の言い回しでその単語に触れている可能性が高い(例: あるページでは
「永久の歯車」、別のページでは「止まらぬ機構」のように、同じ対象を指す表現が
親ごとに違う)。

- 各隠しページのエントリに`keywords`配列を追加する(`title`とは別に持つ)。
  表示に使う正式名称は`title`のまま変えず、`keywords`は検索マッチ専用の
  隠しフィールドとする。
- 検索処理は`title`+`category`+`keywords`の全要素を対象にした部分一致に拡張する。
- 4節の表で親IDが複数あるページを実装する際は、**各親ページで実際に埋め込んだ
  単語・言い回しを漏れなく`keywords`に登録すること**(親ごとに表現が違っても、
  どちらでもヒットするようにするため)。
- 親が1つだけのページは、無理に複数の言い回しを用意しなくてよい
  (`keywords`は`title`と同じ1件だけでも問題ない)。
- **重要な制約(2026-07-28 ユーザー指示)**: 1ページが複数の`keywords`を持つのはOKだが、
  **同じキーワード文字列を複数の異なるページが持ってはいけない**(多対1はOK、
  1対多はNG)。同じ語句が2ページの`keywords`に重複すると、検索結果が曖昧になり
  「どちらのページを指しているか分からない」状態になってしまう。新しい隠しページを
  実装する際は、`src/search-data.js`内の既存エントリ全ての`keywords`と重複しないか
  必ず確認すること。検索の土台整備(5節)の完了条件として、`tests/`に重複検出の
  テストを追加し`npm run test`で機械的に検証されるようにすること(例: 全エントリの
  `title`+`category`+`keywords`を平坦化し、重複が無いことを確認するテスト)。

- **`exactMatch`フィールド(2026-07-29 ユーザー指摘・確定)**: 上記の部分一致は
  通常の検索語には適しているが、謎解きの合言葉(断片の到達先ページ)にまで
  部分一致を適用すると、答えの一部を入力しただけで偶然ヒットしてしまう
  (例: 答えが「HAGURUMA」の場合、「HAGURU」でも一致してしまう)。断片の
  到達先ページのエントリには`exactMatch: true`を設定し、その場合のみ
  `title`/`category`/`keywords`のいずれかとの**完全一致**(大文字小文字は
  区別しない)でのみヒットするようにする。判定ロジックは`src/logic.js`の
  `filterSearchIndex`・`src/search.js`の`filterIndex`に実装済み。通常の
  discoveryエントリ(`exactMatch`を設定しないもの)はこれまで通り部分一致のまま。

### 2-2. 保持する情報(`localStorage`)

ノスティオンは「学院で起きたことを何でも記録する」という設定のため、
`localStorage`にも2種類の情報を**別々の領域**として保持する(2026-07-28
ユーザー指示: 「訪問した」と「断片を手に入れた」は本来別の状態であり
同じ扱いにしない)。

- **学院の秘密**(訪問済みの隠しページ): そのページの`path`のみを配列で保持する。
  検索ゲーティング(下記)にのみ使う。
- **手にした断片**: 断片ID(`F1`等)の配列を保持する。ページを開いただけでは
  記録されず、暗号を解く・合言葉を当てる等、そのページ固有のアクションを
  達成した時にのみ追加される(「学院の秘密」とは獲得タイミングが異なりうる)。
  各断片は以下も併せて保持する:
  - `foundAt`: どのページで見つけたか(ノスティオンの記録表示で参照)
  - `used`: 中間断片(2-1節、F2/F6/F9/F10)が、それを必要とするページの謎解きに
    実際に使われたかどうかのフラグ。使用済みかどうかで記録表示の見せ方を
    変える(例: 使用済みの断片は「役目を終えた」ことが分かるような表現にする)。
    扉用の断片(直接扉に使うもの)は、扉を開いた時点でまとめて`used`にする。
- 保持内容のイメージ(キー名・構造は実装時に決定してよい):
  ```
  {
    "secrets": ["glossary/mythical-creatures.html", …],
    "fragments": [
      { "id": "F1", "foundAt": "glossary/perpetual-motion.html", "used": false },
      …
    ]
  }
  ```

### 2-3. 検索ゲーティング(適当な単語で先読みできないようにする仕組み)

- `src/search-data.js`の各隠しエントリに`prereq`フィールドを持たせる:
  - `null`(または省略): 常に検索可能(通常ページや既存ギミックから直接たどり着く
    「入口」ページはこれ)
  - 文字列配列(直前に訪れているべきページのpathの候補一覧): 網状構造により
    複数の経路から同じページにたどり着けるため、**配列のうちどれか1つでも
    「学院の秘密」に含まれていればOK**というOR判定にする(全部訪問している
    必要はない)。単一経路しかない場合は要素数1の配列でよい。
- 判定ロジックは`src/logic.js`にテスト可能な純粋関数として実装する
  (例: `isSearchEntryUnlocked(entry, visitedPaths)`。`entry.prereq`が`null`なら
  常に`true`、配列なら`visitedPaths`との積集合が1つ以上あれば`true`)。
- 部分一致検索そのものは変更しない(厳しくするのはゲート判定のみ。正規のプレイの
  快適さは損なわない)。
- 既存の4ページ(魔法生物図鑑・永久運動術式・魔導88星座・決闘王列伝)は
  `prereq: null`のまま(現状維持、変更不要)。

## 3. 表の読み方

| 列 | 意味 |
|---|---|
| ID | このドキュメント内だけで使う仮のページ番号 |
| 種別 | `root`=通常ページ/既存ギミックから直接たどり着く入口、`flavor`=前段のページから続く読み物、`fragment`=断片を産出するページ、`gate`=扉ページ、`final`=ゴール |
| たどり着き方 | どのIDから見つかるか。**網状構造のため、複数のIDから同じページにたどり着けてよい**(例: P1にもP14にも同じ単語が出てきて、どちらからでもP20が見つかる、など)。その場合はIDをカンマ区切りで並べる。`root`は代わりに発見元(通常ページ内の語句 or 既存ギミック名)を書く |
| 産出する断片 | このページで手に入る断片のID(無ければ空欄) |
| 必要な断片 | このページの謎を解く/たどり着くために事前に必要な断片のID(無ければ空欄) |
| status | `未着手` / `実装済み(実ファイルパス)` |

断片は `F1`〜`F14` の14種類。うち扉ページに直接必要なのは
**F1・F3・F4・F5・F7・F8・F11・F12・F13・F14の10種**。F2・F6・F9・F10は中間断片
(それぞれP21、P32、P93、P94を解くためだけに使われ、扉ページには直接使わない)。

`F1`等の記号はこの設計図の中だけで使う内部管理用IDであり、ユーザーには見せない。
実装時には各断片に必ず「○○の断片」という個別名を付ける(例: F1の
「刻の断片」、F2の「記帳の断片」)。「○○」の部分は、その断片が手に入るページ・
ギミックの内容に応じてその都度考える(例: 決闘王列伝がらみの断片なら
「決闘王の断片」、時計塔がらみなら「刻の断片」のように)。ノスティオンの
「集めた断片」表示(4-7節参照)でも、`F1`ではなくこの個別名を表示する。

**注意(命名の衝突回避、2026-07-28。2026-07-29解消)**: P3のページタイトルは
元々`魔導88星座 星図の断片`で、この断片命名パターンが決まる前から存在する
既存ページ名だった。「断片」という語がARGの仕組み上の特別な意味を持つように
なった今、P3が汎用的な単語「断片」だけの部分一致で検索にヒットしてしまうと
紛らわしい(ノスティオンの説明を読んで「断片」という言葉に興味を持った人が、
意味もなくP3に行き着いてしまう)という懸念があった。**2026-07-29、P7の謎解き
(位置・配置方式)がP3の星座名を参照する形に作り直したのを機に、P3のタイトルを
「魔導88星座」に改題し「断片」の語を削除、懸念自体を解消した。** 他の断片
アイテムの個別名を決める際も、既存ページタイトルと完全一致する名前は避けること。

**注意(自己言及ワードとの衝突回避、2026-07-28実装時に判明)**: P91の実装により、
検索欄で「私」「ノスティオン」を含む問いかけはノスティオン自身への自己言及として
特別扱いされるようになった(`src/search.js`の`isCodexSelfReference`)。今後
P番号ページの`title`/`keywords`を決める際、これら2語を単体または主要な部分
として含めないこと(含めてしまうと、そのページを探しているつもりが自己言及の
特別な応答に横取りされてしまう)。

**「ノスティオンの独り言」演出(2026-07-28 ユーザー指示)**: 隠しページ本文末尾の
`.glossary-footnote`のように、意味深に読める一文(例: 魔導88星座ページの
「天球儀に刻まれた88座のうち、逸話として文章に残っているのはこの数座のみです。
残りは、まだ誰も語っていないだけなのかもしれません……。」)は、地の文のままではなく
「ノスティオンの独り言」という小見出し(ラベル)を添えた一区画として見せる
(本文の内容自体は変更しない、framingのみの変更)。これは新規に追加した4隠しページ
(魔法生物図鑑・永久運動術式・魔導88星座・決闘王列伝)の`.glossary-footnote`全てが
対象で、今後P番号ページを実装する際も、同様に意味深な締めの一文を置く場合は
同じ「ノスティオンの独り言」ラベルの演出を使うこと(検索ページ自体の誘導文
`.codex-hint`はノスティオンが利用者に直接語りかける呼びかけであり、独り言では
ないため対象外)。

**次に検索すべき語句は独り言に置かない(2026-07-29 ユーザー指摘・方針確定)**:
次のページへの発見経路となる検索語句(`keywords`に対応する文字列)そのものは、
`.glossary-footnote`(「ノスティオンの独り言」)ではなく、`.archive-entry__lore`
等の本文側に置くこと。独り言はあくまで雰囲気のための余韻であり、謎解きの
手がかりそのものの置き場所にはしない、という区別を明確にするため。P97
(`time-ring-record.html`)・P98(`time-ledger.html`)は当初この区別に反して
「刻の声」という語句を独り言側に置いていたが、本文側(縁石の銘・欄外の走り書き)
に移設して修正済み。**既存ページのうち`glossary/dueling-champions.html`
(独り言に「静寂の一撃」)・`glossary/perpetual-motion.html`(独り言に
「修繕工房」を含む一文)の2件がこの方針に反したまま残っている。今後の
サイクルで本文側への移設を行うこと(`docs/ROADMAP.md`「### 13」にtodoとして
記載)。**

**本文の語り手ルール(2026-07-29 ユーザー指摘・方針確定)**: P5「見習い整備士の
手記」・P7「記録帳、最後の頁」の謎解き文中に「どこかで見た覚えのある記号だ、
という気がするが」「この記録帳の書き出しには、いつも決まった4つの言い回しが
あった気がする」のような主観的な一文(暗黙にノスティオンの語りとして書いた
つもりだった)が入っていたが、その同じ段落の中で「ノスティオンに尋ねてみて」
と外部の誰かに呼びかけており、ノスティオンがノスティオンに尋ねろと言う矛盾に
なっていた。**`.glossary-footnote`(「ノスティオンの独り言」)以外の本文
(`.archive-entry__lore`・`.origin-story__paragraph`等)では、ノスティオン自身の
語り(主観・独白・「〜という気がする」等)を一切使わないこと。** 代わりに:
- 単なる客観的な記録・資料の説明として書く(誰の視点でもない、資料そのものの
  記述。P1〜P4の大半のカタログ的な文章がこれにあたる)。
- 手記・記録帳・書簡など「書いた人」が明確な資料の場合は、その人物の一人称
  視点で書く(例: P7の手記本文は天文官オーレン自身の言葉として書く)。
既存のP5・P7の該当箇所はこの方針に反しているため作り直しが必要
(`docs/ROADMAP.md`「### 13」に反映済み)。今後新たにP番号ページを実装する際も、
この語り手ルールを最初から満たすこと。

## 4. ページ接続図(初期骨組み。上限は設けない)

**PGATEの開け方について(2026-07-29 ユーザー指摘・方針確定)**: 「必要な断片
F1,F3,F4,...」は、断片を単純な所持チェック(インベントリの鍵アイテムのように
「持っているか/持っていないか」だけで判定する)にはしない。**断片そのものを
「使う」のではなく、その断片を獲得する過程で登場した謎解きギミック(記号↔読み
の対応表)を、扉ページでもう一度使う**、という体験にする。扉ページには
(獲得済みの断片に対応する)記号列が複数並んでおり、プレイヤーが「あ、これは
刻の断片を取った時に見た、あの術式記号だ」と気づき、対応するP番号ページで
学んだ変換規則を再び適用して読み解く、という形にする。そのため、各fragment
種別のページで使う暗号・記号体系は、**扉ページで再登場させても意味が通る
再利用可能なものにすること**(一度きりの使い捨ての謎にしない)。実装時は、
どの断片がどの記号体系に対応するかをこの節か5節に一覧化しておくこと。

**再利用ギミックの使用済み一覧**:
- フィンレー式記譜法(P2/P5、記号→アルファベット1文字): 🜂=H・🜁=A・🜃=G・
  🜄=U・🜅=R・🜆=M(以上F1「歯車」で使用)。🜇=T・🜈=S・🜉=N・🜊=K・🜋=O・
  🜌=I(ダミー、未使用)。
- 魔導88星座(P3/P7、番号+ひらがな名の何文字目か): 第07番かぎあな座・
  第23番がらすびん座・第41番ゆれふりこ座・第56番ふたごぼし座・
  第74番わすれしお座(以上F2「流れ星」で使用)。

**今後の拡充方針(2026-07-29 ユーザー提案)**: 上記2つの体系は、今後新規に
実装する別のP番号ページ(root/flavorどちらでもよい)にも、さりげなく新しい
魔導88星座(番号+ひらがな名)やフィンレー式記譜法の新規記号↔アルファベット
対応を登場させ、PGATEで使えるだけの素材を少しずつ蓄積していく。狙いは
2つ: (a) P3・P2に頼らず様々なページに星座・記号の手がかりが散らばることで

星座番号(1〜88の中で未使用の番号を選ぶ)・記号(フィンレー式記譜法のダミー
枠、または新しい記号を追加)と重複させないこと。**

## 5. 実装の進め方(evolveループ向け)

- `### 13`のタスクとして着手する際は、このファイルの「未着手」の行を1つ(または
  関連する2〜3行)選び、実際のページタイトル・本文・(該当すれば)暗号やギミックの
  具体的な中身を決めて実装する。
- **実装順序(依存関係)**: 選ぼうとしている行の「必要な断片」欄に断片IDが
  書かれている場合、その断片を産出する行(4節の表を`(P◯◯産出)`で逆引きできる)が
  まだ「未着手」なら、先にそちらを実装すること(存在しない断片を前提にした
  ページを作らないため)。例: P21は「必要な断片: F2(P7産出)」なので、P7が
  実装済みでない限りP21は選べない。P93→P94のような入れ子チェーン(4-4b節)は
  必ずP92→P93→P94の順に実装する。「たどり着き方」の親ページ(root)は、
  多くの場合すでに実装済み(既存4ページ)か、先に選んで実装するため大きな問題には
  ならないが、迷ったら親→子の順で選ぶこと。この順序ルールは`tests/`の
  断片依存順序テスト(`docs/ROADMAP.md`「### 15」参照)で機械的にも検証される。
- 「たどり着き方」が「通常ページ(未定)」の行を選んだ場合、既存サイトの本文を
  棚卸しして実際にふさわしい語句を選定してから実装する(今までの`### 13`と同じ
  やり方)。
- **root優先(2026-07-28 ユーザー指摘・方針確定)**: 依存関係上どちらも選べる
  状態(未着手かつ前提ページが実装済み)の行が複数ある場合、`種別`が`flavor`/
  `fragment`(既存の隠しページからさらに奥へ辿るもの)より、`root`(通常ページの
  本文から新しく生えるもの、4-2節「通常ページ発の新規ルート群」に多い)を
  優先して選ぶこと。既存4ページ(P1〜P4)の枝だけを深く掘り進めるより、サイト内
  の新しい入口(root)を先に増やす方が、プレイヤーが偶然ARGに気づくきっかけを
  広げられる。ただし絶対的な規則ではなく、同じサイクルでまとめて実装する方が
  自然な組み合わせ(例: 断片の産出行と、それを直後に使う行)がある場合は
  そちらを優先してよい。
- 実装したら、このファイルの該当行に実ファイルパスを追記し、statusを更新する。
- **新しい隠しページを実装する際は毎回**: 本文中の言及箇所自体は残しつつ説明を
  加えすぎないこと(発見価値を損なわないため)。網状構造で複数の親を持つページは、
  各親ページの言い回しを`keywords`に漏れなく登録すること。
- 断片を産出するページ(`fragment`種別)を実装する際は、断片の受け渡し方(暗号の答え・
  合言葉など)を明記し、その断片を必要とする側のページ(`必要な断片`欄で参照される側)
  が実装される時に矛盾しないようにする。**あわせて`src/fragment-names.js`に
  その断片ID→「○○の断片」個別名のエントリを必ず追記すること**(忘れると
  ノスティオンの記録表示に内部ID(`F1`等)がそのまま出てしまう)。
  - **謎解き必須(2026-07-28 ユーザー指摘・方針確定)**: P5・P7・P91(F1・F2・F13)は
    いずれも「ページに辿り着いて訪問しただけ」で断片を自動獲得する実装になって
    しまっており、上記の「断片の受け渡し方」の趣旨(暗号の答え・合言葉など)に
    反していた。**今後新たにfragment種別のページを実装する際は、単純訪問での
    自動獲得を禁止**し、必ず何らかの実際の謎解きアクション(ページ内の暗号を
    解読して答えを検索窓に入力する、複数の選択肢から正解を選ぶ、既出の情報を
    組み合わせないと導けない合言葉を入力する、等)を経て初めて断片を獲得する
    実装にすること。具体的な謎解きの形式は各ページの内容に応じて実装時に
    検討してよい。**既に実装済みのP5・P7・P91分も含め、この方式に作り直すことが
    確定した(2026-07-28 ユーザー承認)。作り直しタスクは`docs/ROADMAP.md`
    「### 13」に個別のP番号ごとのサブタスクとして追記済み。**
    - **やり直し(2026-07-29)**: P5・P7の最初の作り直しは、答えとなる単語
      (「はぐるま」「もどりば」)をページ本文にそのまま書いてしまっており、
      「暗号を解読する」という体裁だけで実質的な謎解きになっていなかった
      (ユーザー指摘により発覚、両ページとも実装を差し戻し済み)。
      正しい実装方針は次の3点:
      1. **答えを本文に直接書かない**。答えを導くための「材料」だけを、
         複数のページに分けて置く(例: 断片ページAに暗号表・対応表を置き、
         断片ページBに暗号化された符丁だけを置く。プレイヤーはAの対応表を
         Bの符丁に当てはめて初めて答えを得られる、というように)。
      2. **記号は単純な図形(◇▽○△等)ではなく、魔法学院というコンセプトに
         沿ったモチーフにすること**(2026-07-29 ユーザー指摘)。例えば魔法陣の
         ルーン・術式紋様・星座記号・錬金術記号など、既存ページに登場する
         世界観要素を流用・派生させる。
      3. **謎解きの答え(検索窓に入力させる単語)はひらがなではなくローマ字
         (アルファベット表記)にすること**(2026-07-29 ユーザー指摘: 「ひらがなは
         ダサい」)。`src/search.js`の検索は大文字小文字を区別しない部分一致
         なので、ローマ字表記の合言葉でも実装上の問題はない。
      4. **記号↔読みの対応表は、その断片専用の使い捨てにせず、PGATE(4-6節)で
         再登場させる前提で設計すること**(2026-07-29 ユーザー指摘。詳細は
         4-6節「PGATEの開け方について」参照)。断片は所持チェックのアイテムでは
         なく、扉ページで再び使う「解読方法を覚えているか」のテストとして機能する。
      5. **同じ謎解きギミックを複数の断片で使い回さないこと**(2026-07-29
         ユーザー指摘: 「謎解きのギミックすべて記号と対応文字でやろうとしてない?」
         「同じギミックを使うの禁止で」)。上記1〜4は「記号↔読みの対応表」という
         1つの実装例に過ぎず、P5・P7・P91以降のすべての断片をこの同じ方式
         (記号を対応表で1文字ずつ置き換える)で作ると単調になる。断片ごとに
         異なる仕組みを採用すること。具体的な方式は各断片の実装時に検討し、
         `docs/ROADMAP.md`の該当タスクに明記した上で、**それまでに実装済みの
         全ての断片(P5に限らず)のいずれとも重複しないものを選ぶこと**。
      - **訂正(2026-07-29 ユーザー指摘、レビューにて判明)**: 上記3.の
        ローマ字化ルールは、P5の対応表(記号→読み)の**表示上の話**であり、
        謎解きの最終的な答え(検索窓に入力させる単語)を一律ローマ字にする
        という意味ではなかった。P7(「MODORIBA」)・P91(「MEMORIA」
        「VERITAS」「ORIGO」)まで最終的な合言葉をローマ字・ラテン語化して
        しまったのは誤った一般化であり、作り直しが必要。正しくは:
        - **検索窓に入力させる最終的な合言葉は、自然な日本語の単語(漢字や
          ひらがななど通常の表記)にすること**。P5の場合は「HAGURUMA」では
          なく「歯車」のように。
        - 謎解きの過程(対応表・アクロスティック等)で、記号や頭文字から
          **読み(音)**を中間的に導く手段としてローマ字を使うこと自体は
          問題ない(例: P5は記号から1文字ずつアルファベットを導き、
          つなげると「haguruma」という読みになり、そこから実際の単語
          「歯車」に気づく、という流れにする)。
      - **P5の対応表そのものの訂正(2026-07-29 ユーザー指摘)**:
        - **1記号=1モーラ(2文字、例: 🜂=「HA」)ではなく、1記号=1アルファベット
          (1文字)にすること**。この対応表はPGATE(4-6節)で他の単語の解読にも
          再利用される前提のため、モーラ単位ではなく1文字単位の汎用的な
          換字式暗号表であるべき。
        - **対応表には、この謎解きに必要な記号だけでなく、今回は使わない
          ダミーの記号↔文字のペアも増やして載せること**(ユーザー指摘:
          「なぜなら扉でも使うから」)。狙いは2つ: (a) 表を見ただけでは
          どの記号が今回必要かすぐには分からず謎解きの難度が保たれる、
          (b) PGATEで別の単語を解読する際にも同じ表を参照できるだけの
          文字種をあらかじめ揃えておける。
        - この変更に伴い、P5の物理的な符丁(現在は歯車4枚歯=4記号、
          4モーラ「は/ぐ/る/ま」に対応)も、1文字ずつのアルファベット表現
          (「haguruma」なら8文字分の記号が必要)に合わせて作り直しが必要。
          歯車のモチーフのまま歯の数を増やすか、別の物理表現に変えるかは
          実装時に検討する。
- **1ページあたりの情報量(2026-07-28 ユーザー指摘・方針確定)**: P5〜P8は
  既存4ページ(P1〜P4、各2〜5項目のカタログ形式)と比べて1ページに項目が
  1つしかなく、見劣りするとの指摘を受けた。**今後新たに実装するP番号ページ
  (root/flavor/fragment問わず)は、1ページにつき関連する項目を2〜3個程度
  持たせ、P1〜P4に近い情報量を目安にすること**(単一の短い引用・断片文だけで
  完結させない)。**既存のP5〜P8・P91のページも同水準まで項目を追加することが
  確定した(2026-07-28 ユーザー承認)。作り直しタスクは`docs/ROADMAP.md`
  「### 13」に個別のP番号ごとのサブタスクとして追記済み(上記の謎解き対応と
  同じタスクにまとめてある)。**
- 検索ゲーティングの仕組み(2節)は、隠しページを1つでも新規実装する前に
  土台として先に作ること。
- ページ数・接続は目安であり、実装を進める中で自然に変わってよい
  (例えば断片の受け渡し方が思ったより不自然なら、その場でこのファイルを修正する)。
  ただし「扉ページが要求する断片の一覧」を変える場合は、既に実装済みの断片ページとの
  整合性を必ず確認すること。
- **素材の依頼(2026-07-28 ユーザー指示)**: P番号のページ(フレーバー・断片問わず)を
  実装する際、イラストやナレーションがあれば深みが増すと判断した場合は、
  テキストのみで済ませず`docs/ASSET_REQUESTS.md`の「依頼中」へ積極的に依頼を
  追記すること(既存の「素材の積極依頼」方針と同じ扱い)。全ページに必須では
  ないが、扉ページ・ゴールページのような節目のページや、雰囲気を大きく左右する
  ページでは特に検討すること。
